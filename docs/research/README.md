# 調査ノート

技術選定や仕様調査の記録。**追記のみで、後から結論が変わっても消さない。**
「なぜその案を採ったか」だけでなく「なぜ他の案を採らなかったか」を残す場所。

将来プラットフォームを追加するとき(Google Meet / Teams など)や、
技術スタックを見直すときに、当時どの選択肢をどう評価したかをここで辿れる。

## ノート一覧

| ノート | 調査したこと | 結論 |
|---|---|---|
| [000-initial-notes](./000-initial-notes.md) | プロジェクト開始時の雑多メモ。要件・疑問点・代替案の一次ソース | 表示方式は Electron 透過ウィンドウを採用(2026-09-04 追記) |

現在有効な結論は [docs/decisions/](../decisions/README.md)、
作業の詳細は [docs/plan/](../plan/README.md) を見ること。

## いつ書くか

**複数の選択肢を評価して 1 つを選ぶとき**に書く。具体的には以下。

- SDK / ライブラリ / ツールの選定
- アーキテクチャの分岐(A 案と B 案のどちらを採るか)
- 対応プラットフォームの追加検討

逆に、選択肢が 1 つしかない調査や、単に手順を調べただけのものは書かない。
それは Plan の「分かったこと」に 1〜2 行で足せば足りる。

## 書き方

1. [TEMPLATE.md](./TEMPLATE.md) をコピーして `docs/research/<slug>.md` を作る。
   slug は調査対象が分かる名前にする(`meeting-sdk-selection` など)。連番は振らない
   (`000-initial-notes.md` だけは例外。プロジェクト開始時の一次ソースなので先頭に置く)
2. **調べる前に「確認項目」を先に書く。** 候補ごとに違う物差しで測らないため
3. 候補を調べ、一次ソースの URL と確認日を残す
4. 採用と却下を決め、**却下理由を必ず書く**
5. このファイルの「ノート一覧」に 1 行足す
6. 結論を [docs/decisions/](../decisions/README.md) へ反映する
7. 関連する Plan の「分かったこと」からこのノートへリンクする(内容は複製しない)

## 守ること

- **却下した候補を消さない。** 却下理由が将来の再検討の出発点になる
- **一次ソースの URL と確認日を必ず残す。** 仕様は変わる。いつ時点の情報かが分からないと
  再調査のとき使えない。公式ドキュメントを優先し、ブログや Stack Overflow だけで判断しない
- **ドキュメントに書いてあったことと、実際に動かして観測したことを区別する。**
  前者は「〜と記載されている」、後者は「〜を確認した」と書き分ける
- **「未確認のまま残したこと」を空にしない。** ドキュメントを読んだだけで
  全部分かることはまずない。実機で確かめる項目とその TODO を明記する
- **結論が変わっても上書きしない。** 追記して、いつ何が変わったかを残す。
  「今どうなっているか」は decisions が持つので、ここは履歴でよい

## 将来プラットフォームを追加するとき

Google Meet / Teams 対応を検討する段になったら、まず既存のノートを読む。
Zoom のときにどの物差しで測ったかが「確認項目」に残っているので、
同じ項目で新しいプラットフォームを評価すれば横比較できる。

新しいノートを `docs/research/<platform>-<topic>.md` として足し、
既存ノートは書き換えない。
